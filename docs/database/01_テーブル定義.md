# 社員管理システム 要求仕様書

## 1. システム概要

本システムは、管理者が社員情報を管理し、社員が社員情報を閲覧・更新するためのWebアプリケーションである。

ログイン認証および権限管理に使用する情報は`users`テーブルで管理し、社員番号、氏名、メールアドレス、部署、役職、入社日および在籍状態は`employees`テーブルで管理する。

ログインアカウントを持っていない利用者は、未ログイン状態でユーザー登録を行う。ユーザー登録では`users`テーブルだけに情報を登録し、`employees`テーブルには社員情報を登録しない。

管理者は、登録済みのUserを指定して社員情報を登録する。登録されたEmployeeは、`employees.user_id`によってUserと1対1で関連付ける。

管理者はログイン後、社員情報の一覧表示、登録、更新、削除およびCSVファイルによる一括登録・更新を行うことができる。

社員はログイン後、社員一覧を閲覧できる。また、自身に関連付けられた社員情報のうち、氏名および社員情報用メールアドレスを更新できる。

## 2. 用語定義

| 用語 | 説明 |
| --- | --- |
| User | システムへログインするための認証情報および権限情報 |
| Employee | 社員番号、氏名、部署、役職などの社員情報 |
| ログイン用メールアドレス | `users.email`に保存し、ログイン認証に使用するメールアドレス |
| 社員情報用メールアドレス | `employees.email`に保存し、社員情報として表示するメールアドレス |
| 未関連ユーザー | Userは存在するが、Employeeと関連付けられていないEMPLOYEEユーザー |
| 管理者 | `users.role`が`1`のユーザー |
| 社員 | `users.role`が`0`であり、Employeeと関連付けられたユーザー |

## 5. データ管理方針

### 5.1 Usersテーブル

`users`テーブルは、ログイン認証および権限管理に使用する。

管理対象は次のとおりとする。

- ユーザーID
- ログイン用メールアドレス
- パスワードハッシュ
- 権限

ユーザー登録では`users`テーブルだけに情報を登録する。

### 5.2 Employeesテーブル

`employees`テーブルは、社員情報の管理に使用する。

管理対象は次のとおりとする。

- 社員ID
- 関連するユーザーID
- 部署ID
- 役職ID
- 社員番号
- 氏名
- 社員情報用メールアドレス
- 入社日
- 在籍状態

社員登録では`employees`テーブルに情報を登録する。社員登録機能から`users`テーブルへの新規登録は行わない。

### 5.3 Departmentsテーブル

`departments`テーブルは、社員が所属する部署を管理するマスターテーブルとする。

初期データは次のとおりとする。

| コード | 表示名 |
| --- | --- |
| `GENERAL` | 総務 |
| `HR` | 人事 |
| `PLANNING` | 企画 |
| `SALES` | 営業 |

### 5.4 Positionsテーブル

`positions`テーブルは、社員の役職を管理するマスターテーブルとする。

初期データは次のとおりとする。

| コード | 表示名 |
| --- | --- |
| `STAFF` | 一般社員 |
| `LEADER` | 主任 |
| `MANAGER` | 課長 |
| `DIRECTOR` | 部長 |
| `EXECUTIVE` | 本部長 |
| `CEO` | 社長 |

## 6. テーブル間の関連

### 6.1 UsersとEmployees

```text
users.id
   ↓
employees.user_id
```

- UserとEmployeeは1対0または1の関係とする。
- Employeeは必ず1件のUserと関連付ける。
- `employees.user_id`には既存の`users.id`を設定する。
- `employees.user_id`は一意とし、同一Userを複数のEmployeeへ関連付けない。
- UserはEmployeeと関連付けられていない状態でも存在できる。
- ADMINユーザーはEmployeeとの関連付けを必須としない。
- EMPLOYEEユーザーが社員向け機能を利用するには、Employeeとの関連付けを必要とする。

### 6.2 DepartmentsとEmployees

```text
departments.id
   ↓
employees.department_id
```

- 1つの部署には複数の社員が所属できる。
- 1人の社員は1つの部署に所属する。
- `employees.department_id`には、`departments`テーブルに存在するIDを設定する。

### 6.3 PositionsとEmployees

```text
positions.id
   ↓
employees.position_id
```

- 1つの役職には複数の社員を関連付けられる。
- 1人の社員は1つの役職を持つ。
- `employees.position_id`には、`positions`テーブルに存在するIDを設定する。

## 7. 登録フロー

```text
1. 利用者がユーザー登録を行う
             ↓
2. usersテーブルにログインアカウントを登録する
             ↓
3. 利用者がログインする
             ↓
4. 管理者が未関連Userを指定して社員登録を行う
             ↓
5. employeesテーブルに社員情報を登録する
             ↓
6. employees.user_idにusers.idを設定する
```

- User登録後は、`users`テーブルの情報を使用してログインできる。
- EMPLOYEEユーザーは、Employeeとの関連付けが完了するまで社員一覧および自身の社員情報を利用できない。
- 未関連のEMPLOYEEユーザーには、ログイン後に関連付け待ち画面を表示する。

## 9. 機能要件

### 9.1 ユーザー登録

#### 9.1.1 概要

ログインアカウントを持っていない利用者が、未ログイン状態で自身のログインアカウントを登録する。

#### 9.1.2 入力項目

| 項目 | 必須 | 入力制限 |
| --- | :---: | --- |
| メールアドレス | ○ | 254文字以内、メールアドレス形式、重複不可 |
| パスワード | ○ | 8～64文字 |
| パスワード確認 | ○ | パスワードと一致すること |
| 登録種別 | ○ | `EMPLOYEE`または`ADMIN` |
| 管理者登録情報 | 条件付き必須 | ADMIN登録時に必要 |

#### 9.1.3 要件

- 未ログイン利用者が実行できる。
- `users`テーブルにユーザー情報を登録する。
- `employees`テーブルへの登録・更新は行わない。
- メールアドレスは`users`テーブル内で重複できない。
- パスワードはBCryptでハッシュ化して保存する。
- パスワードの平文をデータベースおよびログに保存しない。
- EMPLOYEEとして登録する場合は、`users.role`に`0`を設定する。
- ADMINとして登録する場合は、`users.role`に`1`を設定する。
- クライアントから送信された権限値を無条件に保存しない。
- ADMIN登録時は、管理者登録コードなどの管理者であることを確認できる情報をバックエンドで検証する。
- 登録成功後はログイン画面へ遷移する。

> [!NOTE]
> 現在の`users`テーブルにはアカウント状態を表すカラムがないため、登録完了後のUserは直ちにログイン可能となる。

### 9.2 ログイン

#### 9.2.1 入力項目

| 項目 | 必須 | 入力制限 |
| --- | :---: | --- |
| メールアドレス | ○ | 254文字以内、メールアドレス形式 |
| パスワード | ○ | 8～64文字 |

#### 9.2.2 要件

- `users.email`を検索キーとしてUserを取得する。
- 入力されたパスワードと`users.password`に保存されたBCryptハッシュ値を照合する。
- `employees.email`はログイン認証に使用しない。
- 認証成功時はJWTを発行する。
- JWTからUser IDおよび権限を識別できること。
- UserがEmployeeと関連付けられていないことだけを理由にログインを拒否しない。
- 未関連のEMPLOYEEユーザーは、ログイン後に関連付け待ち画面へ遷移する。
- 未ログイン状態では、認証が必要な機能へアクセスできない。
- 認証失敗時は、メールアドレスの登録有無を推測できない共通メッセージを表示する。
- JWTには有効期限を設定する。

### 9.3 ログアウト

- クライアント側で保持しているJWTを削除する。
- ログアウト後はログイン画面へ遷移する。
- ログアウト後、認証が必要な画面へアクセスした場合はログイン画面へ遷移する。

### 9.4 社員一覧表示

#### 9.4.1 管理者の表示項目

- 社員番号
- 氏名
- 社員情報用メールアドレス
- 部署名
- 役職名
- 入社日
- 在籍状態

#### 9.4.2 社員の表示項目

- 氏名
- 社員情報用メールアドレス
- 部署名
- 役職名

#### 9.4.3 要件

- `employees`テーブルから社員情報を取得する。
- 部署名は`departments`テーブルを参照して取得する。
- 役職名は`positions`テーブルを参照して取得する。
- 初期表示は社員番号の昇順とする。
- 管理者は社員一覧から更新・削除対象を選択できる。
- 更新・削除対象は`employees.id`で特定する。
- EMPLOYEEユーザーには`ACTIVE`の社員だけを表示する。

### 9.5 社員登録

#### 9.5.1 入力項目

| 項目 | 必須 | 入力制限 |
| --- | :---: | --- |
| ユーザー | ○ | Employeeと未関連のUserから選択 |
| 社員番号 | ○ | 半角数字5桁、重複不可 |
| 氏名 | ○ | 1～50文字 |
| メールアドレス | ○ | 254文字以内、メールアドレス形式、重複不可 |
| 部署 | ○ | `departments`テーブルに存在する値 |
| 役職 | ○ | `positions`テーブルに存在する値 |
| 入社日 | ○ | `yyyy-MM-dd`形式 |
| 在籍状態 | ○ | `ACTIVE`または`RETIRED` |

#### 9.5.2 要件

- ADMINユーザーのみ実行できる。
- `employees`テーブルに社員情報を登録する。
- 社員登録機能から`users`テーブルへの新規登録は行わない。
- 登録済みかつEmployeeと未関連のUserを指定する。
- 選択したUserのIDを`employees.user_id`へ設定する。
- 既にEmployeeと関連付けられているUserは選択できない。
- 選択された部署のIDを`employees.department_id`へ設定する。
- 選択された役職のIDを`employees.position_id`へ設定する。
- 社員番号、社員情報用メールアドレスおよびUser IDは重複できない。
- 氏名は空白文字だけでは登録できない。

> [!NOTE]
> 要求上の社員番号は半角数字5桁とする。テーブルの`VARCHAR(20)`は格納可能な最大長であり、アプリケーションとデータベースのCHECK制約で5桁を保証する。

推奨するデータベース制約は次のとおりである。

```sql
CHECK (employee_number ~ '^[0-9]{5}$')
```

### 9.6 社員更新

- ADMINユーザーのみ実行できる。
- 社員一覧から更新対象社員を選択する。
- 更新対象は`employees.id`で特定する。
- 対象Employeeが存在しない場合は新規登録せず、404エラーとする。
- 通常の社員更新ではUpsertを行わない。
- 氏名、社員情報用メールアドレス、部署、役職、入社日および在籍状態を更新できる。
- 社員番号および`user_id`は変更できない。
- Employeeのメールアドレスを更新しても、`users.email`は更新しない。
- 部署および役職には、それぞれのマスターテーブルに存在するIDだけを設定できる。

### 9.7 社員削除

- ADMINユーザーのみ実行できる。
- 社員一覧から削除対象社員を選択する。
- 削除対象は`employees.id`で特定する。
- 確認ダイアログ表示後に削除する。
- 対象Employeeと関連するUserを物理削除する。
- EmployeeとUserの削除は同一トランザクションで行う。
- 外部キー制約を考慮し、Employeeを削除した後にUserを削除する。
- いずれかの削除に失敗した場合は、すべての削除を取り消す。

> [!WARNING]
> 物理削除を行うと履歴が失われる。履歴保持が必要になった場合は、Employeeを`RETIRED`に変更し、Userに有効状態を表すカラムを追加して無効化する方式へ変更する。

### 9.8 CSVインポート

#### 9.8.1 ファイル仕様

| 項目 | 仕様 |
| --- | --- |
| ファイル形式 | CSV |
| 文字コード | UTF-8 |
| 区切り文字 | カンマ |
| 1行目 | ヘッダー |
| 日付形式 | `yyyy-MM-dd` |

#### 9.8.2 CSV項目

| CSV項目 | 必須 | 用途 |
| --- | :---: | --- |
| `user_email` | ○ | 関連付けるUserの検索 |
| `employee_number` | ○ | Employeeの登録・更新判定 |
| `name` | ○ | 氏名 |
| `email` | ○ | 社員情報用メールアドレス |
| `department` | ○ | 部署名 |
| `position` | ○ | 役職名 |
| `hire_date` | ○ | 入社日 |
| `status` | ○ | 在籍状態 |

#### 9.8.3 登録・更新判定

| 条件 | 処理 |
| --- | --- |
| `employee_number`が存在しない | Employeeを新規登録する |
| `employee_number`が存在する | 既存Employeeを更新する |

#### 9.8.4 新規登録要件

- `user_email`に一致するUserが存在すること。
- 対象Userが他のEmployeeと関連付けられていないこと。
- Userが存在しない場合は自動登録せず、エラーとする。
- `department`に一致するDepartmentが存在すること。
- `position`に一致するPositionが存在すること。
- 存在しない部署または役職が指定された場合はエラーとする。

#### 9.8.5 更新要件

- `employee_number`に一致するEmployeeを更新する。
- 既存Employeeの`user_id`および社員番号は変更しない。
- `user_email`が既存の関連Userと一致しない場合はエラーとする。
- Employeeのメールアドレスを更新しても、`users.email`は更新しない。

#### 9.8.6 共通要件

- ADMINユーザーのみ実行できる。
- CSVインポートでは`users`テーブルを登録・更新しない。
- CSV内で社員番号、社員情報用メールアドレスまたはUserメールアドレスが重複する場合はエラーとする。
- 必須項目が不足している場合はエラーとする。
- 1行でもエラーがある場合は、全件の登録・更新を取り消す。
- エラー時は行番号、項目名およびエラー内容を表示する。
- 成功時は登録件数および更新件数を表示する。

### 9.9 社員自身の情報更新

#### 9.9.1 更新可能項目

- 氏名
- `employees.email`に保存された社員情報用メールアドレス

#### 9.9.2 要件

- EMPLOYEEユーザーのみ実行できる。
- JWTからログイン中のUser IDを取得する。
- `employees.user_id`を使用して本人のEmployeeを特定する。
- リクエストで指定されたUser IDまたはEmployee IDだけを信用して更新対象を決定しない。
- ログイン中のUserと関連するEmployeeだけを更新できる。
- 社員番号、部署、役職、入社日、在籍状態およびUserとの関連は変更できない。
- Employeeのメールアドレスを変更しても、`users.email`は変更しない。
- ログイン用メールアドレスの変更は、本機能の対象外とする。

## 10. 部署・役職マスター

### 10.1 部署マスター

- `departments`テーブルには初期データを登録する。
- 社員登録・更新画面では、`departments`テーブルから選択肢を取得する。
- 社員一覧では、Employeeに関連する部署名を表示する。
- 現時点では部署の追加・更新・削除画面を実装しない。

### 10.2 役職マスター

- `positions`テーブルには初期データを登録する。
- 社員登録・更新画面では、`positions`テーブルから選択肢を取得する。
- 社員一覧では、Employeeに関連する役職名を表示する。
- 現時点では役職の追加・更新・削除画面を実装しない。

## 13. 共通エラー仕様

| HTTPステータス | 内容 |
| ---: | --- |
| `400 Bad Request` | 入力内容不正 |
| `401 Unauthorized` | 未認証またはJWTが無効 |
| `403 Forbidden` | 権限不足 |
| `404 Not Found` | 対象データが存在しない |
| `409 Conflict` | メールアドレス、社員番号またはUser関連の重複 |
| `500 Internal Server Error` | システム内部エラー |

入力エラー時は、原則として次の情報を返す。

- エラーコード
- 対象項目
- エラーメッセージ
- CSVの場合は行番号

システム内部の例外内容、SQLおよびスタックトレースは利用者へ表示しない。

## 14. 非機能要件

| 項目 | 内容 |
| --- | --- |
| 認証 | `users`テーブルのメールアドレスとパスワードを使用してJWT認証を行う |
| 認可 | バックエンドの各APIで`users.role`を検証する |
| パスワード | BCryptでハッシュ化し、平文を保存またはログ出力しない |
| JWT | 有効期限を設定し、JWTをアプリケーションログへ出力しない |
| 通信 | 本番環境ではHTTPSを使用する |
| データ整合性 | 主キー、外部キー、一意制約、NOT NULL制約およびCHECK制約によって保証する |
| トランザクション | 複数テーブルを操作する処理は同一トランザクションで実行する |
| CSV | 1件でもエラーがある場合は全件をロールバックする |
| 保守性 | Controller、ServiceおよびRepositoryの責務を分離する |

## 17. 現行テーブル定義に関する注意事項

### 17.1 Userの有効・無効状態

現在の`users`テーブルには有効・無効状態を保持するカラムがない。そのため、ユーザー登録後は直ちにログイン可能となる。

管理者承認やアカウント無効化を実装する場合は、`users`テーブルに`status`または`enabled`カラムを追加する。

### 17.2 物理削除

現在の仕様では、社員削除時にEmployeeと関連Userを物理削除する。監査履歴を保持する必要がある場合は、次の変更を検討する。

- Employeeは削除せず、`status`を`RETIRED`へ変更する。
- Userに有効・無効状態を追加する。
- 退職時はUserを無効化し、ログインを禁止する。

### 17.3 監査および同時更新

現在のテーブル定義には、次のカラムが存在しない。

- `created_at`
- `updated_at`
- `created_by`
- `updated_by`
- `version`

監査記録または楽観ロックを要件に含める場合は、対象テーブルへの追加が必要である。
