# テーブル定義書（社員管理システム）

## 1. Usersテーブル

### 1.1 概要

ログイン認証および権限管理に使用するユーザー情報を管理するテーブル。

### 1.2 カラム定義

| カラム名 | 型 | 必須 | PK | UNIQUE | 説明 |
| --- | --- | :---: | :---: | :---: | --- |
| `id` | `BIGSERIAL` | ○ | ○ | - | ユーザーID |
| `email` | `VARCHAR(254)` | ○ | - | ○ | ログイン用メールアドレス |
| `password` | `VARCHAR(60)` | ○ | - | - | ハッシュ化済みパスワード |
| `role` | `SMALLINT` | ○ | - | - | ユーザー権限 |

### 1.3 制約

- PRIMARY KEY：`id`
- UNIQUE：`email`
- NOT NULL：`email`
- NOT NULL：`password`
- NOT NULL：`role`
- CHECK：`role IN (0, 1)`

### 1.4 値制約

#### `role`

| 値 | 説明 |
| ---: | --- |
| `0` | EMPLOYEE |
| `1` | ADMIN |

### 1.5 CRUD仕様

#### CREATE

- 新規ユーザー登録時に、ログインに必要なユーザー情報を登録する。

#### READ

- ログイン認証時に、メールアドレスを検索キーとしてユーザー情報を取得する。

#### UPDATE

- パスワード、メールアドレスおよび権限の更新処理は、現時点では実装しない。

#### DELETE

- 管理者による社員削除時に、対応するEmployeesテーブルおよびUsersテーブルのデータを物理削除する。

---

## 2. Employeesテーブル

### 2.1 概要

社員番号、氏名、メールアドレス、部署、役職、入社日および在籍状態を管理するテーブル。

管理者による社員情報の登録・更新・削除、CSVインポート、社員自身の情報取得・更新処理で使用する。

### 2.2 カラム定義

| カラム名 | 型 | 必須 | PK | UNIQUE | 説明 |
| --- | --- | :---: | :---: | :---: | --- |
| `id` | `BIGSERIAL` | ○ | ○ | - | 社員ID |
| `user_id` | `BIGINT` | ○ | - | ○ | Usersテーブルに対応するユーザーID |
| `department_id` | `BIGINT` | ○ | - | - | Departmentsテーブルに対応する部署ID |
| `position_id` | `BIGINT` | ○ | - | - | Positionsテーブルに対応する役職ID |
| `employee_number` | `VARCHAR(20)` | ○ | - | ○ | 社員番号 |
| `name` | `VARCHAR(50)` | ○ | - | - | 氏名 |
| `email` | `VARCHAR(254)` | ○ | - | ○ | 社員情報用メールアドレス |
| `hire_date` | `DATE` | ○ | - | - | 入社日 |
| `status` | `VARCHAR(20)` | ○ | - | - | 在籍状態 |

### 2.3 制約

- PRIMARY KEY：`id`
- UNIQUE：`user_id`
- UNIQUE：`employee_number`
- UNIQUE：`email`
- NOT NULL：`user_id`
- NOT NULL：`department_id`
- NOT NULL：`position_id`
- NOT NULL：`employee_number`
- NOT NULL：`name`
- NOT NULL：`email`
- NOT NULL：`hire_date`
- NOT NULL：`status`
- FOREIGN KEY：`user_id REFERENCES users(id)`
- FOREIGN KEY：`department_id REFERENCES departments(id)`
- FOREIGN KEY：`position_id REFERENCES positions(id)`
- CHECK：`status IN ('ACTIVE', 'RETIRED')`

### 2.4 値制約

#### `status`

| 値 | 説明 |
| --- | --- |
| `ACTIVE` | 在籍 |
| `RETIRED` | 退職 |

### 2.5 CRUD仕様

#### CREATE

- 管理者は社員情報を新規登録できる。
- 管理者はCSVインポートによって社員情報を一括登録できる。
- 管理者による社員登録時は、Employeesテーブルに社員情報を登録する。
- 社員登録処理では、Usersテーブルへログイン情報を新規登録しない。
- 社員登録時は、部署および役職に対応するIDを`department_id`と`position_id`へ設定する。

#### READ

- 管理者は社員情報を一覧取得できる。
- 社員は自身の情報を編集する際に、自身の社員情報を取得できる。
- 社員は社員一覧画面で、社員の氏名、メールアドレス、部署および役職を取得できる。
- 部署および役職を表示する場合は、DepartmentsテーブルとPositionsテーブルを参照する。

#### UPDATE

- 管理者は社員情報を更新できる。
- 社員は自身の氏名およびメールアドレスのうち、Employeesテーブルに格納された情報だけを更新できる。
- 画面から社員情報を更新する場合は、`employees.id`を検索キーとして使用する。
- 社員のメールアドレスを更新しても、Usersテーブルの`email`は同時に更新しない。
- CSVインポート時は、既存の社員情報を更新できる。

#### DELETE

- 管理者のみ社員情報を物理削除できる。
- 社員情報を削除する場合は、対応するUsersテーブルのユーザー情報も削除する。

### 2.6 登録・更新ルール

- 画面から社員情報を更新または削除する場合は、`employees.id`を検索キーとして使用する。
- Usersテーブルとの関連付けには、`employees.user_id`を使用する。
- Departmentsテーブルとの関連付けには、`employees.department_id`を使用する。
- Positionsテーブルとの関連付けには、`employees.position_id`を使用する。
- CSVインポート時は、`employee_number`を基準として新規登録または更新を判定する。
- CSV内の社員番号がEmployeesテーブルに存在しない場合は、新規登録する。
- CSV内の社員番号がEmployeesテーブルに存在する場合は、既存の社員情報を更新する。
- `id`はデータベースによって自動採番されるため、CSVの登録・更新判定には使用しない。

## 3. Departmentsテーブル

### 3.1 概要

社員が所属する部署情報を管理するマスターテーブル。

### 3.2 カラム定義

| カラム名 | 型 | 必須 | PK | UNIQUE | 説明 |
| --- | --- | :---: | :---: | :---: | --- |
| `id` | `BIGSERIAL` | ○ | ○ | - | 部署ID |
| `name` | `VARCHAR(50)` | ○ | - | ○ | 部署名 |

### 3.3 制約

- PRIMARY KEY：`id`
- UNIQUE：`name`
- NOT NULL：`name`

### 3.4 初期値

#### `name`

| 値 | 説明 |
| --- | --- |
| `GENERAL` | 総務 |
| `HR` | 人事 |
| `PLANNING` | 企画 |
| `SALES` | 営業 |

### 3.5 CRUD仕様

#### CREATE

- 管理者は部署情報を新規登録できる。
- 使用する部署情報は、初期データとしてあらかじめ登録する。

#### READ

- 管理者および社員は部署情報を取得できる。
- 社員登録画面および社員更新画面で、部署の選択肢として取得する。
- 社員一覧画面で、社員が所属する部署を表示するために取得する。

#### UPDATE

- 管理者のみ部署情報を更新できる。
- 部署情報を更新する場合は、`departments.id`を検索キーとして使用する。

#### DELETE

- 現時点では部署の削除処理を実装しない。
- 削除処理を実装する場合は、Employeesテーブルから参照されている部署を削除できないものとする。

### 3.6 登録・更新ルール

- 部署情報の登録および更新は、Departmentsテーブルに対して行う。
- 社員情報を登録または更新する場合は、選択された部署の`departments.id`を取得する。
- 取得した部署IDを`employees.department_id`へ設定する。
- CSVインポート時は、CSVに記載された部署名から対応する部署情報を検索する。
- 取得した部署IDを`employees.department_id`へ設定する。
- Departmentsテーブルに存在しない部署名がCSVに記載されている場合はエラーとする。

## 5. テーブル間の関連

各テーブルは、Employeesテーブルが保持する外部キーカラムを使用して関連付ける。

### 5.1 Usersテーブルとの関連

```text
users.id
   ↓
employees.user_id
```

- `users.id`と`employees.user_id`を関連付ける。
- 1件のユーザー情報に対して、最大1件の社員情報を関連付ける。
- `employees.user_id`にはUNIQUE制約を設定する。
- Employeeは必ず1件のUserと関連付ける。
- UserはEmployeeと関連付けられていない状態でも存在できる。

### 5.2 Departmentsテーブルとの関連

```text
departments.id
   ↓
employees.department_id
```

- `departments.id`と`employees.department_id`を関連付ける。
- 1つの部署には複数の社員が所属できる。
- 1人の社員は1つの部署に所属する。

### 5.3 Positionsテーブルとの関連

```text
positions.id
   ↓
employees.position_id
```

- `positions.id`と`employees.position_id`を関連付ける。
- 1つの役職には複数の社員を関連付けることができる。
- 1人の社員は1つの役職を持つ。

### 5.4 関連付けに関する注意事項

- `users.id`と`employees.id`は直接関連付けない。
- `users.id`と`employees.user_id`を関連付ける。
- `departments.id`と`employees.department_id`を関連付ける。
- `positions.id`と`employees.position_id`を関連付ける。
- テーブル間の関連は、アプリケーション側だけでなくデータベースの外部キー制約によって保証する。
- 社員情報、部署情報および役職情報をまとめて取得する場合は、JOINまたはJPAの関連付けを使用する。

## 6. ER関係概要

```text
Users (1) ───── (0..1) Employees
                         │
                         ├──── (N:1) Departments
                         │
                         └──── (N:1) Positions
```

| 親テーブル | 親カラム | 子テーブル | 子カラム | 関係 |
| --- | --- | --- | --- | --- |
| `users` | `id` | `employees` | `user_id` | 1対0または1 |
| `departments` | `id` | `employees` | `department_id` | 1対多 |
| `positions` | `id` | `employees` | `position_id` | 1対多 |
